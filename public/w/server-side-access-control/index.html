登入牆要擋在伺服器，不是畫面

我做一個只有平台管理員能用的工具頁，驗證只寫了一個小函式，卻擋在三個地方。這裡面有一個很多人會寫錯的觀念：能不能做，只能在伺服器判斷，不能靠畫面。

用 Next.js，有些檔案長得像前端 React，其實跑在伺服器上。看「在哪裡跑」，不要看「長得像什麼」。

核心：一個守門函式

一個共用的驗證函式

export async function verifyPlatformAdmin() {
  const supabase = await createServerClient();
  const { data: { user } } = await supabase.auth.getUser();   // ① 你是誰
  if (!user) return { authorized: false, error: "請先登入" };

  if (!isPlatformAdminId(user.id))                            // ② 在不在名單上
    return { authorized: false, error: "無權限存取" };

  return { authorized: true, userId: user.id };               // ③ 過關
}
  • ① 你是誰：伺服器拿瀏覽器帶來的登入憑證，去問認證系統「這張憑證是誰的」。不是相信瀏覽器自己說「我是某某某」。getUser() 會把 token 拿回去跟認證系統核對，偽造或過期的當場被打回。
  • ② 在不在名單上：拿帳號 ID 去比對名單。名單放在伺服器的環境變數裡，名字前面沒有 NEXT_PUBLIC_，不會被打包進前端，瀏覽器看不到。
  • ③ 過關：把確認過的帳號 ID 交回去。後面的程式用這個 ID，不用瀏覽器傳來的任何身分資料。

名單沒設時，解析出來是空的，任何人比對都不會中 → 沒有人是管理員，而不是人人都過。用帳號 ID 不用 Email：Email 可以改，ID 不會變。

為什麼每一層都要自己驗一次

關鍵在第 2 層。那些開站、儲存的函式，檔案開頭是 "use server"，代表只在伺服器執行，但它們同時也是外面打得到的入口——不經過頁面也能直接呼叫。所以每一個的第一行都要自己驗：

"use server";

export async function instantCreate(input) {
  const auth = await verifyPlatformAdmin();          // 第一行就驗
  if (!auth.authorized) return { error: auth.error };
  // ...通過了才往下做,而且掛在 auth.userId 名下
}

第 1 層頁面擋住的，只是「不是管理員就看不到畫面」。第 2、3 層才是真的門鎖。畫面藏不藏按鈕是好不好看的問題，不是安全的問題。

為什麼不能只在畫面那邊擋

只在畫面上擋

「不是管理員就不顯示按鈕」。按鈕不見了，但後面的入口還開著。懂的人不用按鈕，直接對入口送請求，一樣能做。

在伺服器擋

不管請求從哪來、畫面被怎麼改，每個入口都先確認身分。畫面只是方便，不是防線。

記一句話就好：畫面決定看起來怎樣，伺服器決定能不能做。 攻擊者站在網路外面，他只能控制送進來的輸入（網址、標頭、cookie），碰不到你伺服器裡跑的程式。所以判斷放在伺服器才有意義。

怎麼確認真的擋住

拿三種身分分別打三個入口，看回應。管理員全過，其他兩種在每一層都被擋——這就是上面那個小實驗在演的。

這套做法避開的三個常見錯

  • 把名單放到瀏覽器看得到的地方（例如 NEXT_PUBLIC_ 開頭的變數）。名單外流，等於告訴別人該去偷哪個帳號。
  • 用 Email 當身分。Email 可以改，也可能被別種登入方式綁到同一個信箱。
  • 名單沒設就當作通過。設定漏一次，整個後台就對所有人打開。這裡反過來：沒設就全部擋。
